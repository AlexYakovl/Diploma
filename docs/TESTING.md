# Руководство по тестированию

В репозитории используются NUnit 4 для модульных тестов и интеграционное тестирование ASP.NET Core. Основной набор запускает реальный HTTP-конвейер API через `WebApplicationFactory`, изолированную SQLite-базу EF Core и тестовую схему аутентификации.

## Стратегия тестирования

### Модульные тесты

Модульные тесты проверяют модели и DTO без внешних сервисов:

- обязательные поля и ограничения длины;
- значения по умолчанию для модерации отзывов и сортировки категорий;
- стандартное поведение сущностей приложения.

### API-тесты

API-тесты запускают реальное приложение ASP.NET Core и проверяют:

- HTTP-статусы и содержимое ответов;
- аутентификацию JWT и защищённые маршруты;
- изменения в изолированной базе данных;
- валидацию входных данных;
- загрузку и обработку изображений;
- негативные сценарии и отсутствующие сущности.

Матрица основных зон покрытия:

| Зона | Проверяемые сценарии |
|---|---|
| Аутентификация | корректные и некорректные данные входа, JWT, `/me`, защищённые endpoints |
| Категории | получение списка, вложенные альбомы, создание, обновление, удаление, валидация |
| Альбомы | публичное чтение, фильтрация, CRUD, проверка обложки |
| Фотографии | получение фотографий, отсутствующие записи, загрузка PNG и обработка файлов |
| Отзывы | публичный и админский список, модерация, видимость, удаление |
| Hero и About | публичные списки, некорректные изображения, служебные операции |
| HTTP-конвейер | неизвестный маршрут, авторизация и заголовок подтверждения очистки |

Набор содержит **45 NUnit-тестов**: модульные проверки моделей и интеграционные API-тесты.

## Архитектура тестов

- `PhotoSite.Api.Tests/PhotoSiteWebApplicationFactory.cs`
  - запускает реальное приложение API;
  - заменяет PostgreSQL изолированной SQLite-базой в памяти;
  - создаёт тестового пользователя Identity и начальные категории с альбомом;
  - подключает тестовую аутентификацию.
- `PhotoSite.Api.Tests/TestAuthHandler.cs`
  - разрешает тестовый principal только при заголовке `X-Test-Auth: true`;
  - не изменяет `[Authorize]` и production-код контроллеров.
- `PhotoSite.Api.Tests/ApiEndpointsTests.cs`
  - отправляет реальные HTTP-запросы через `WebApplicationFactory`;
  - проверяет статусы, полезную нагрузку и поведение негативных сценариев.
- `PhotoSite.Api.Tests/ModelValidationTests.cs`
  - проверяет аннотации DTO и сущностей.

Успешный вход в систему по-прежнему проверяет реальную генерацию JWT. Защищённые routes проверяются как с тестовой аутентификацией, так и без неё.

## Запуск тестов

Восстановить пакеты и собрать решение:

```powershell
dotnet restore PhotoSite.sln
dotnet build PhotoSite.sln --no-restore
```

Запустить все NUnit-тесты:

```powershell
dotnet test PhotoSite.sln --configuration Debug
```

Запустить только тестовый проект API:

```powershell
dotnet test PhotoSite.Api.Tests/PhotoSite.Api.Tests.csproj --configuration Debug
```

Запустить с подробным выводом NUnit:

```powershell
dotnet test PhotoSite.sln --logger "console;verbosity=normal"
```

Запустить отдельный класс или тест:

```powershell
dotnet test PhotoSite.Api.Tests/PhotoSite.Api.Tests.csproj --filter FullyQualifiedName~ApiEndpointsTests
dotnet test PhotoSite.Api.Tests/PhotoSite.Api.Tests.csproj --filter Name~Login
```

## Покрытие кода

Собрать отчет по покрытию в формате OpenCover:

```powershell
dotnet test PhotoSite.Api.Tests/PhotoSite.Api.Tests.csproj `
  --collect:"XPlat Code Coverage" `
  --results-directory TestResults
```

При необходимости сформировать HTML-отчет:

```powershell
dotnet tool install -g dotnet-reportgenerator-globaltool
reportgenerator "-reports:TestResults/**/coverage.cobertura.xml" "-targetdir:TestResults/coverage-html" "-reporttypes:Html"
```

Отчет о покрытии является дополнительной аналитикой, а не заменой проверки продуктовых сценариев и негативных путей. Репозиторий не заявляет обязательное достижение 100% покрытия веток.

## CI в GitHub Actions

Workflow запускается для push и pull request в ветку `main` и выполняет:

1. восстановление NuGet-пакетов;
2. Release-сборку всего решения;
3. запуск всех NUnit-тестов;
4. создание TRX-отчета;
5. публикацию результатов тестирования как артефакт workflow.

Слияние изменения следует считать неготовым, если сборка завершается с ошибками или хотя бы один NUnit-тест падает.

Известные NuGet Audit-предупреждения рассматриваются отдельно от прохождения тестов. На момент создания набора production-проект содержит advisory-уведомления для `SixLabors.ImageSharp 3.1.12`; успешные тесты не отменяют необходимость обновления уязвимой зависимости.

## Изоляция тестовых данных

Каждая test-factory получает отдельное SQLite-соединение в памяти. Данные Identity и каталога создаются в setup-фазе. Класс API-тестов помечен `[NonParallelizable]`, чтобы тестовые HTTP-запросы и файловые операции не пересекались.

При добавлении нового теста следует:

1. сформулировать измеримый результат;
2. выбрать модульный или API-тест;
3. использовать независимый fixture и очистку состояния;
4. проверять статус, payload и изменения базы данных;
5. не использовать fixed sleep, внешнюю сеть или production-секреты.
